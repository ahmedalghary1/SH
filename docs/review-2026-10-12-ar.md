# تقرير مراجعة وإصلاح SH ERP — 12 أكتوبر 2026

## النتيجة وحدود التحقق

نُفذت الإصلاحات في ملفات المشروع المحلية، مع الحفاظ على التصميم الحالي وإضافة تحسينات محدودة لتسهيل الاستخدام. أُجريت اختبارات قواعد البيانات على قواعد منفصلة ببيانات اصطناعية، ولم تُنفذ عمليات حفظ أو تعديل أو حذف على بيانات الموقع المنشور.

الموقع المنشور `https://sh.elwsamstore.com/` أعاد 500 عند محاولة تسجيل الدخول أثناء الفحص. الصفحة العامة لتسجيل الدخول كانت متاحة، وكذلك فحص الصحة وملفات PWA العامة. لم تتوفر سجلات Passenger/Django أو صلاحية نشر على السيرفر؛ لذلك لا يمكن الجزم بأن السبب الفعلي لذلك الخطأ قد زال في النسخة المنشورة. الإصلاحات تعالج أسبابًا مثبتة في الكود، ويحتاج تأكيد نتيجة الإنتاج إلى نشرها وفحص السجل عند أي خطأ متبقٍ.

قاعدة `db.sqlite3` الأصلية بقيت كما كانت عند بدء العمل، بما فيها التغييرات الموجودة قبل هذه المراجعة. بصمة SHA256 المسجلة للمقارنة:

```text
EF2F5C427A41A2B5A8EC0193A733BDEF72ABC26C66BEA233813E853DC62FD0F8
```

لا يتضمن هذا الإصدار تغييرًا في هيكل قاعدة البيانات أو ترحيلًا يعيد كتابة البيانات القديمة. ملف التسليم يستبعد قواعد البيانات وملفات المستخدمين وملفات البيئة الخاصة.

## حذف الفاتورة

أضيف رابط حذف للمدير من قائمة الفواتير وصفحة تفاصيلها، يفتح صفحة توضح أثر العملية قبل التأكيد. الحذف يُنفذ بطلب POST وبصلاحيات الحذف الموجودة، داخل معاملة واحدة:

1. إعادة الكمية إلى مخزنها الأصلي مع الاحتفاظ بتكلفة المخزون التاريخية.
2. عكس الدفعات الفعلية في الخزن التي استقبلتها، مع عكس حصة الفاتورة فقط من التحصيل العام للعميل.
3. إلغاء المديونية المتبقية وعكس التسويات المرتبطة عند وجودها.
4. إزالة الفاتورة من قائمة الفواتير النشطة مع الاحتفاظ بالفاتورة والطلب والمدفوعات وسجل التدقيق للمراجعة.

الضغط المتكرر لا يعيد الكمية أو يعكس النقود مرتين. إذا فشل أي جزء، تُلغى العملية كلها. إذا كانت هناك مرتجعات مرتبطة، أو تحصيل مندوب تم تسليمه، أو لم تكفِ الخزنة لعكس الدفعة، تظهر رسالة توضح سبب منع الحذف. هذا يمنع تغيير أرصدة مرتبطة دون تسوية. تعديل الفاتورة وحذفها يحتاجان اتصالًا بالسيرفر.

## تحسين الاستخدام دون إعادة تصميم

- منع تكرار الحفظ مع إعادة تمكين الزر عند فشل التحقق أو إلغاء العملية.
- منع نتائج بحث أو مخزون متأخرة من استبدال الاختيار الأحدث داخل الفاتورة.
- تحسين البحث داخل القوائم واستخدام الأسهم وEnter وEscape، وإدارة التركيز داخل النوافذ.
- تصحيح إجمالي الشراء مع الخصم والمدفوع، وإصلاح تعديل الصنف بعد حذف صف سابق.
- إبقاء الهاتف والمعرّفات وأكواد المنتجات دون فواصل رقمية تُفسدها.
- تحسين عرض الهاتف، والتبويبات، وحالة التحميل ورسائل الخطأ، وإظهار الأسماء كنص آمن.
- إظهار عدد العمليات المعلقة وزر مراجعتها، مع وقت العملية ورقمها ورسالة فشل المزامنة وإمكانية تنزيل نسخة منها.

ما يحتاجه الاستخدام اليومي بعد النشر: تدريب قصير على الفرق بين «محفوظ محليًا» و«تمت المزامنة»، وفتح الجهاز أول مرة أثناء الاتصال، وتحديد الأشخاص المخولين بالحذف وتسوية العهدة. يُفضَّل اختبار دورة فاتورة كاملة على جهاز Android وجهاز iPhone وطابعة الفواتير المستخدمة فعليًا؛ ذلك لم يمكن التحقق منه عن بُعد.

## PWA والعمل دون اتصال

أُضيف عزل بيانات المتصفح حسب المستخدم والمعرض والصلاحية، وحفظ محلي ذري للعمليات، وتجديد الجلسة وCSRF قبل المزامنة، ومنع تكرار الأثر على السيرفر حتى عند إرسال متزامن من تبويبين. التعارضات تبقى ظاهرة للمراجعة، والمحاولات المؤقتة تتكرر تدريجيًا مع الاحتفاظ بنفس رقم العملية.

التحديث لا يعيد تحميل نموذج غير محفوظ أو يتجاوز عمليات معلقة. تحميل الصفحات مسبقًا محدود لتخفيف الحمل على السيرفر. أخطاء 403 و500 تبقى واضحة ولا تُغطى بصفحة قديمة. لا يُعاد إرسال POST إذا انقطع الرد بعد إرساله، لأن العملية قد تكون نُفذت بالفعل.

العمل دون اتصال يشمل النماذج المدعومة لإنشاء مستندات البيع والعملاء وعدد من حركات المخزون والتحصيل والمنتجات والمشتريات والمرتجعات والعهدة، وفق صلاحيات الحساب. لا تصبح الفاتورة المحلية نهائية إلا بعد قبولها على السيرفر. المخزون المحلي تقديري ولا يمنح ضمان توفر عند المزامنة. تسجيل الدخول، والتعديل والحذف المالي للفواتير القائمة، وبعض الإجراءات والتقارير تحتاج الاتصال.

قاعدة PWA القديمة المشتركة لم تُحذف، ولم تُنقل عملياتها تلقائيًا بين الحسابات لعدم وجود إثبات كافٍ لمالك كل عملية ومعرضها. إذا توجد عمليات قديمة لم تُزامن على جهاز، يجب تسويتها أو استخراجها من النسخة القديمة قبل تحديث ذلك الجهاز. مسح بيانات المتصفح قد يفقد العمليات التي لم تصل للسيرفر؛ زر تنزيل العمليات يوفر نسخة للمراجعة.

التفاصيل الفنية في [توثيق PWA](pwa_offline_sync.md).

## التحقق

- مجموعة اختبارات Django الكاملة مرت على PostgreSQL وSQLite. اختبار التزامن الخاص بـPostgreSQL يُتخطى على SQLite.
- اختبارات JavaScript الـ17 نجحت؛ تشمل العزل بين الحسابات، ومنع إعادة إرسال POST، وإظهار 403/500، وسلوك النماذج وإجمالي الشراء.
- فحوص Django و`makemigrations --check --dry-run` وفحص أسماء Python غير المعرفة نجحت. لا توجد تغييرات هيكل جديدة.
- اختُبرت صفحات إضافة وتعديل الفاتورة وتفاصيلها وتأكيد حذفها بعرض هاتف 390 بكسل؛ جرى أيضًا حفظ عميل محليًا ثم مزامنته. Chromium اختُبر بمحاكاة قطع الشبكة، وWebKit بمحاكاة عدم توفر السيرفر. اختبارات WebKit على Windows لا تغني عن اختبار Safari على iPhone فعلي.
- اختُبر عدم تغيير قاعدة البيانات الأصلية بمقارنة البصمة قبل العمل وبعده.

نجاح الاختبارات يثبت الحالات المغطاة؛ لا يُعد ضمانًا بأن كل حالة في بيانات الإنتاج أو إعدادات الاستضافة قد فُحصت.

## نشر آمن على السيرفر الحالي

1. احتفظ بنسخة موثقة من PostgreSQL وملفات المستخدمين والنسخة الحالية من الكود و`.env`. اختبر استعادة نسخة قاعدة البيانات في قاعدة منفصلة. لا تستخدم بيانات العملاء الحقيقية لإجراء تجربة بيع أو حذف على الموقع الفعلي.
2. راجع بيانات الاتصال الخاصة الحالية. استخدم `DB_ENGINE=postgres` وقيم `POSTGRES_*` الحالية، أو أسماء الإعدادات القديمة المدعومة. لا تستبدل `.env` بملف المثال الذي يختار SQLite محليًا؛ لا تنشئ قاعدة جديدة بدل القاعدة الحالية.
3. انشر ملفات الكود كاملة. لا تستبدل قاعدة البيانات أو مجلد الوسائط أو مجلد النسخ الاحتياطية. ملف المصدر المضغوط لا يحتوي هذه البيانات.
4. داخل بيئة Python الخاصة بالموقع، نفذ:

```sh
python -m pip install -r requirements.txt
python manage.py check
python manage.py migrate --plan
python manage.py collectstatic --noinput
```

لا يوجد ترحيل جديد في هذا الإصدار. إذا عرضت خطة الترحيل ترحيلات قديمة غير مطبقة، راجعها على نسخة مستعادة أولًا قبل تشغيلها في الإنتاج. لا تستخدم `flush` أو تحذف جداول أو تعيد تحميل بيانات ابتدائية على قاعدة الإنتاج.

5. أعد تشغيل التطبيق من إدارة الاستضافة. إذا كان Passenger مضبوطًا على ملف إعادة التشغيل المعتاد، يمكن تنفيذ `touch tmp/restart.txt` من جذر تطبيق الموقع، بعد التأكد من وجود المجلد الصحيح. اجمع الملفات الثابتة وأعد التشغيل ضمن نافذة نشر واحدة لتجنب خلط ملفات إصدارين.
6. تأكد من `DEBUG=False` و`ALLOWED_HOSTS` و`CSRF_TRUSTED_ORIGINS` المناسبة، ومن عرض الملفات الثابتة عبر HTTPS. فعّل حماية ملفات الارتباط عند التأكد من إعداد HTTPS/الوكيل. احتفظ بإعدادات ومسارات الوسائط الحالية.
7. راجع تسجيل الدخول وفحوص الصحة وصفحات إضافة وتعديل الفاتورة على النسخة المنشورة. اختبر البيع والتعديل والحذف والمزامنة ببيانات اختبار على نسخة منفصلة متصلة بقاعدة مستعادة. راقب سجلات Passenger والتطبيق عند ظهور 500، وابحث برقم المتابعة الظاهر للمستخدم.

توصيات تشغيل ضرورية للاستقرار: نسخ PostgreSQL دورية مع تجربة استعادة، ومراقبة أخطاء الطلبات ومساحة القرص وحدود اتصالات قاعدة البيانات، وتغيير أي كلمة مرور كانت مثبتة سابقًا داخل الكود مع تحديث البيئة الخاصة. هذه الإعدادات تحتاج الوصول للاستضافة ولم تُنفذ على السيرفر خلال هذه المراجعة.
